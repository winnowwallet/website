01 / CRYPTOGRAPHYInternal test build

A focused Bitcoin library,
written in Swift.

Can we own a narrow implementation of the keys and signatures Winnow needs, and justify the responsibility that comes with it?

Winnow already implements its wallet and Bitcoin transaction logic in Swift. At the revision we first inspected, its curve operations used P256K, a Swift interface to C libsecp256k1. On the single-key branch that boundary is now Swift: a module inside the wallet repository, NativeSecp256k1, nine files and about nine hundred lines that depend only on Foundation and CryptoKit. Winnow 0.8.7 build 97 ships on it to internal TestFlight testers.

The attraction was being able to follow the types and implementation all the way through: a key, a tweak, a signature, and the mathematics behind them. That part held up. A reader can start at a 256-bit integer in four limbs and arrive at a BIP340 signature without leaving Swift.

The cost is as described below. libsecp256k1 is an established implementation with extensive testing and deliberate treatment of secret operations. Replacing it transfers that responsibility to us, and the first version accepts two gaps on purpose: every operation is variable-time, and secret scalars are not zeroized. Timing and memory contents may depend on keys and nonces. The module's guide and the wallet's own pages say so rather than inheriting the C library's claims.

What is the minimum?

Schnorr still needs secp256k1. Schnorr is the signature scheme; secp256k1 is the curve used by Bitcoin's BIP340. The first build takes the minimum literally. It is a single-key Winnow with shared accounts removed, so the module implements only what the ordinary receive and send path calls: field and scalar arithmetic, point addition and multiplication with a fixed-base table for the generator, compressed and x-only encodings, BIP32 and Taproot tweaks with libsecp256k1's exact validation rules and parity behaviour, BIP340 signing and verification, and the tagged hash.

Transaction formats, wallet policy, networking, backups, and the interface remain in Winnow. MuSig2, script-path multisig, ECDSA, key recovery and ECDH are out of scope for this build, and a backup that carries shared-account records is refused rather than restored without them.

Use Apple where it fits. Keep the library independent.

CryptoKit supplies SHA-256, which the module uses for BIP340's tagged hashes; Security supplies secure randomness. Apple's public P-256 APIs use a different curve from Bitcoin's secp256k1. They do not provide a drop-in BIP340 signer. Native Swift here means owning the Bitcoin curve implementation in Swift, while using supported platform services.

We want the package to build and test without Winnow, and to be useful beyond this app. A possible contribution to Apple's Swift Crypto project is one direction to explore. Its current contribution rules require maintainer agreement and a usable BoringSSL implementation for new APIs. A native Swift backend therefore needs an explicit upstream decision. Apple acceptance and future CryptoKit availability are open questions.

What exists today

Expected answers never come from the code under test. Field, scalar and point tests use fixtures computed in Python integer arithmetic and by a libsecp256k1 x-only oracle; the wallet's BIP32, BIP86, BIP340 and BIP341 vectors run unchanged through the new backend; differential tests compare every public operation with libsecp256k1, and signatures must match it byte for byte under fixed auxiliary randomness. The fuzz harness feeds the same input to both backends. The recorded signet journey creates a wallet, receives, sends and confirms on a real node with the native signature under it, and the shipped binary links no libsecp256k1 at all. Measured on an Apple silicon Mac in a release build: a BIP32 public child takes 52 µs against the C library's 19 µs and a Taproot tweak 50 µs against 22 µs, so address derivation stays within three times; multiplying the generator on its own is 37 µs against 11 µs, about 3.4 times; signing takes 271 µs and verification 207 µs against 26 µs and 18 µs.

The next experiments

  1. Constant time and secret lifetimes. Replace the conditional subtractions, the per-bit branch in scalar multiplication and the secret-indexed table lookup with constant-time selects, clear the scalar copies made while signing and tweaking, and measure what that costs.
  2. Remove the last pin. The test suite still links libsecp256k1 as the differential oracle and for the signet miner's ECDSA signatures. Recorded vectors and a miner signer of its own would leave the repository with no third-party package at all.
  3. Decide where it lives. A separate app identity for the single-key build, so it can be installed beside Winnow; whether the module becomes an independent package or an upstream contribution; and whether shared signing and Silent Payments justify adding the point operations this build left out.
02 / RECOVERYEarly development

Give an old wallet
a way forward.

Winnow Rescue explores how to move funds from older Bitcoin wallet backups into an account the owner already controls.

A backup can outlive the software that created it. Recovery means understanding its format, finding the right keys and outputs, and showing the owner exactly where the money will go. That work deserves a focused tool with explicit limits for every supported format.

Winnow Rescue is being developed separately, with an embeddable Rust core, a command-line interface, and a desktop graphical interface. Its intended destination is an existing Taproot account. Keeping recovery in its own tool lets it address older wallet formats without adding those formats to the everyday phone wallet.

What exists today

The inspected repository contains the initial workspace and interface scaffolding. A complete recovery and sweep workflow has not yet been demonstrated.

The next experiment

Take one precisely defined wallet format through a reproducible test-coin recovery: discover the funds, review the destination and fee, sign, and verify the resulting payment. Test damaged backups, wrong passwords, and interrupted scans before widening support.

03 / BITCOIN SCRIPTSProtocol research

Understand a different
way to commit.

Pay-to-Merkle-Root asks what changes when an output commits directly to a tree of spending scripts.

BIP360 proposes P2MR: script-tree spending without Taproot's key-path spend. We want to understand the consequences for wallet policy, backups, interoperability, and an eventual opt-in migration.

Removing the exposed output key addresses one part of the long-term public-key exposure problem. It does not replace the signatures inside the scripts with post-quantum signatures. That distinction matters when explaining what the proposal could protect.

What exists today

BIP360 is a draft proposal. Winnow's inspected main revision rejects witness-version-2 funding destinations. This is research into future rules, with no Bitcoin activation date or shipping support implied.

The next experiment

Build an isolated experiment with explicit network rules. Check address construction and spending against independent implementations, then exercise backup, restoration, and migration. Record which rules the test network actually enforces.

04 / SIGNING DEVICESCompatibility research

Work with the hardware
people already own.

Can Winnow coordinate payments with an independent signing device, while keeping approval and recovery understandable?

A separate signer can give a wallet a different boundary for key custody. That only helps if the phone and device agree on the account, receiving addresses, spending policy, and transaction being approved. We are researching compatibility with existing hardware wallets.

The full flow matters: what the device can display and verify, how signing messages travel, how shared-signing nonces are used once, and what happens when approval fails. Recovery must cover a lost phone, a replaced signer, and the backups needed to reconstruct the same policy.

What exists today

A preserved Satochip simulator prototype explores signing and recovery. Its pull request is closed and unmerged. Simulation does not demonstrate physical-card operation or iPhone NFC compatibility. The existing Bitcoin Core cosigner guide documents a separate software-signer flow.

The next experiment

Choose a specific hardware model and firmware, then demonstrate receiving, approving, signing, and restoring a test wallet. Publish the coordinator revision, transport, supported policy, and display limitations. Exercise refusal, disconnection, retries, and replacement before claiming compatibility.

05 / PAYMENT PRIVACYProtocol research

Receive repeatedly.
Reveal less.

Can reusable payment information fit a wallet that discovers its own payments on a phone?

BIP352 Silent Payments lets a recipient publish reusable payment information while senders derive separate on-chain output keys. The motivation is to make repeated receiving more practical without putting the same receiving address into every payment.

The tradeoff is discovery. A recipient needs to identify payments intended for them using transaction input information and their scanning key. For Winnow, the research question includes how that work fits its direct-to-peer design, the cost of restoring a wallet, and what the phone must download and compute. Ordinary compact filters alone do not provide everything needed for discovery.

Silent Payments also needs secret scalar multiplication with public points for a shared-secret calculation (ECDH). That would expand the native Swift library beyond the minimum required by current Winnow. We will evaluate that addition explicitly.

What exists today

Winnow currently rejects Silent Payments destinations. BIP352 is a complete specification; light-client discovery remains a research area. Sending, recipient scanning, and recovery need their own Winnow implementation and interoperability evidence.

The next experiment

Start with specification vectors and a test-coin exchange with an independent implementation. Measure the data, time, and energy needed to find and restore payments on an iPhone. Test interrupted scans and chain reorganizations. Make the scanning-key, spending-key, and label recovery requirements explicit, and evaluate any server assistance by what it learns about the recipient.

A question shared by every project

What must survive
the lost device?

A recovery strategy must account for signing authority, coin discovery, spending policy, and any state required to sign safely. Winnow's emphasis on local discovery and Rescue's broader recovery task require separate privacy evaluations: asking a server about wallet-specific scripts or combining coins in a sweep can disclose relationships.

Hash-based signatures make this distinction especially important. SPHINCS+-based SLH-DSA is stateless, but a wallet still needs recoverable keys and account information. Stateful schemes such as XMSS and LMS also require a reliable record of used one-time signing keys. Restoring an old backup can roll that record backward; a chain rescan cannot reveal every signature exported before the device was lost.

These are research questions, not supported post-quantum recovery flows in Winnow or Rescue. The next experiment should specify what is backed up, what can be reconstructed, who learns about the wallet during recovery, and what makes signing safe after restoration.

The standard for every project

Let the evidence
set the pace.

Keep the source inspectable. Name the revision and environment behind a result. Test recovery and failure as deliberately as a successful payment. Measure the costs. A useful research result can be a working implementation, a smaller scope, or a well-supported decision to keep the existing approach.
