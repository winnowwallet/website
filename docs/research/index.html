A wallet should be able to explain its foundations.
Research is how we decide what comes next.

How do we recover older wallets? How much cryptographic code do we need to maintain? What changes when another device signs, or when Bitcoin gains a different way to receive payments?

These projects give those questions room to be tested. Each starts with a reason to investigate, records what works, and names the evidence still missing before we make new promises to people using Winnow.

From the blog: Bitcoin Beyond Conspiracy Theories — where the NIST curve seeds came from, how Bitcoin software gets its secp256k1, and the Swift code behind the first payments.

The first research pass has recorded results and limits. The current work is the Lean 4 app and LeanNative, the framework drawn out of it. Work that has shipped or been set aside stays below as dated history: the native Swift curve, Ledger signing, sending silent payments, and k-of-n accounts with recovery paths.

01 / THE APPCurrent work

The whole wallet,
written in Lean 4.

Can one language hold the wallet, its curve and its screens, with the proofs checked on every build?

Winnow 0.9 is written in Lean 4, in the public winnow-lean repository (MIT; the newest version is v0.9.16, tagged on 17 November 2026). The wallet is Lean: keys, transactions, PSBTs, descriptors, compact-filter sync, peers, the mempool window and the broadcaster over libuv TCP. So is the app's model, update and view, written in the Elm style. Lean compiles it all to C. Standard UIKit controls draw it, through an Objective-C shell that LeanNative prints from Lean at build time. No Swift is compiled, and CI checks every build for Swift.

The curve code behind every key and signature is Winnow's own secp256k1 in Lean, and since 0.9.16 there is one implementation of it: Lean/SecpCt, the field, scalars, points, keys, tweaks, BIP340 and ECDSA on machine words. Signing, deriving keys, Taproot tweaks, sending silent payments and checking signatures all run on it. Each operation is proved against the curve as specified in Lean/Secp, with no axiom beyond Lean's standard three and assuming only that P is prime, and every build checks the proofs. The earlier field code on natural numbers, and the unproved fast path that stood in for its slow parts from 31 October (Lean/Secp/Fast.lean), are deleted. The proofs are about the source. The compiled code is held to answers computed without it, to the vectors of BIP340, BIP32, BIP341 and BIP352, to signatures OpenSSL made, and to Bitcoin Core on regtest.

The code is written to do the same work whatever a secret is: no branch on a secret and no table looked up by one. That the timing does not depend on a key is a property of compiled code. It has been checked only for another build of this source, Linux on x86-64 under Valgrind with the key marked as unknown, not for the arm64 builds the app ships, so the app does not rely on it. The AES behind backup encryption is not constant-time. SECURITY.md says both, and why that is acceptable in a phone wallet that signs only what its owner approves.

Since 0.9.16 the part of the wallet that transaction review needs is also a library of its own, WinnowCore: hashes and the curve, BIP32, transactions, PSBTs and sighashes, descriptors and their addresses, spend review and the header chain, without seed phrases, Unicode tables, coin selection or I/O. CI holds its imports to an allowed list. The Swift app is retired; winnowwallet/winnow keeps its history: its main branch through 0.8.13, and pre-release tags to 0.8.21 on the branches the port followed.

LeanNative is the framework drawn out of Winnow. It gives a Lean app typed capabilities for what only iOS can do: Keychain, Face ID and device authentication, HTTPS GET, Bluetooth LE, CloudKit, background tasks, the clipboard and file paths. Since 0.9.5 the Xcode project is generated from a Lean description of the app, which refuses a capability that lacks its usage text or entitlement, or one the app's code calls without listing it.

Since 2 November LeanNative also owns how an app is tested and released. Its ios-app workflow builds, tests, runs the UI journeys and makes their media; its ios-release workflow turns a version tag into an internal TestFlight build once a full CI run has passed on the same tree (it finds that run and does not test again), and every step of it is a Lean program, leannative-release: the release policy, the signed archive's and exported IPA's checks, and the App Store Connect calls. Winnow's own workflows now name only what is Winnow's: the regtest Bitcoin node, the census peer list and the release notes.

How the app is checked · 17 November

During the port, the Swift WalletCore was the oracle: for each module a Swift driver exercised the original and a Lean program answered the same requests, compared step by step (PORT.md records each run). Every pull request that is ready for review and changes more than the docs, and every push to main, now runs LeanNative's ios-app workflow on GitHub's own macOS runners. The lean job builds the Lean with every proof checked, runs the Lean test programs and, on the 0.9.16 line, five suites against disposable regtest Bitcoin Core nodes (io-test, backend-test, multisig-differential, card-regtest and segwit-regtest), and runs the UI journeys headless. The app job, on two runners at once, builds Debug for the simulator, checks it for Swift and runs the same journeys on an iPhone simulator; a media job joins their recordings into one video. The release job builds Debug and Release for the simulator and Release for devices, checks each for Swift and checks that Release ignores test mode. There are ten journeys on the 0.9.16 line. Main has nine and four regtest suites: it does not have the card for one person yet.

The journeys are Lean programs: named steps of what a person does on each screen, against a regtest node. Controls are named by the same definitions the views use, so a journey that names a control no view has does not compile. Headless, the journeys program runs the app itself as a child, with a stand-in for the native shell, and finds each control in the app's view tree, with no simulator, but this does not test the renderer or real touches. The simulator run does, through XCTest. Its screenshots and recording, with a provenance file naming the commit and the run, are what this site shows: each build of the site takes them from the newest passing run on main and checks every file against the hashes in that file. LeanApp/Journeys.lean holds the journeys.

Lean does not officially support iOS: its runtime libraries are macOS arm64 objects retargeted to the iOS simulator and devices. TestFlight builds 0.9.3 and 0.9.4 ran on the owner's iPhone. On 8 November 2026 LeanNative's own demo app ran on an iPhone 17 Pro Max (iOS 27.2) with a Ledger Nano X: its selftest, the Keychain's device-only class, background tasks that lldb had iOS launch and expire, Face ID and a Bluetooth connection each passed, in two runs, not one. A person runs that check at a Mac; CI does not. Winnow's own background checks and iCloud backup have not run against the shell on a phone.

What's next

  1. Timing on the builds that ship. The proofs now cover the curve code the app runs. That its timing does not depend on a key has been checked only for a Linux x86-64 build under Valgrind. It has not been checked for the arm64 builds the app ships, which use Lean's own runtime.
  2. Run the shell on a physical device. Done in part: LeanNative's demo app has run on an iPhone (above). Winnow's own background checks and iCloud backup have not run against the shell on a phone, and no single device run has passed every check.
  3. Mac Catalyst and Touch ID. Under Catalyst, LeanNative's demo app drops a Touch ID answer given after the app was hidden. This concerns LeanNative's Catalyst support; Winnow has no Catalyst build, and Apple silicon Macs run its iPad app.

Done since 2 November: “Prove the fast curve.” The fast path was not proved; it was replaced. Since 0.9.16 every curve operation the app runs is Lean/SecpCt's, proved against the specification.

Done since 30 October: the manifest now checks the capabilities the app's code calls (#24), and LeanNative v0.2.0 renamed the ElmLean identifiers (#21).

02 / CRYPTOGRAPHYSet aside · history

A focused Bitcoin library,
written in Swift.

Can we own a narrow implementation of the keys and signatures Winnow needs, and justify the responsibility that comes with it?

Set aside, October 2026. The Swift app kept libsecp256k1 in 0.8.13, and the native Swift line and its MuSig2 draft (PRs #235 and #246) were closed. The app then moved to Lean, whose own secp256k1 now does this job (above). This section is the record as of 21 October 2026.

Winnow already implements its wallet and Bitcoin transaction logic in Swift. At the revision we first inspected, its curve operations used P256K, a Swift interface to C libsecp256k1. On the single-key branch that boundary is now Swift: a module inside the wallet repository, NativeSecp256k1, nine files and about nine hundred lines that depend only on Foundation and CryptoKit. Winnow 0.8.7 build 97 shipped on it to internal TestFlight testers; subsequent internal builds are described below.

The attraction was being able to follow the types and implementation all the way through: a key, a tweak, a signature, and the mathematics behind them. That part held up. A reader can start at a 256-bit integer in four limbs and arrive at a BIP340 signature without leaving Swift.

The cost is as described below. libsecp256k1 is an established implementation with extensive testing and deliberate treatment of secret operations. Replacing it transfers that responsibility to us, and the first version accepts two gaps on purpose: every operation is variable-time, and secret scalars are not zeroized. Timing and memory contents may depend on keys and nonces. The module's guide and the wallet's own pages say so rather than inheriting the C library's claims.

What is the minimum?

Schnorr still needs secp256k1. Schnorr is the signature scheme; secp256k1 is the curve used by Bitcoin's BIP340. Build 97 took the minimum literally: a single-key Winnow with shared accounts removed. Its module implements only what the ordinary receive and send path calls: field and scalar arithmetic, point addition and multiplication with a fixed-base table for the generator, compressed and x-only encodings, BIP32 and Taproot tweaks with libsecp256k1's exact validation rules and parity behaviour, BIP340 signing and verification, and the tagged hash.

Transaction formats, wallet policy, networking, backups, and the interface remain in Winnow. MuSig2, script-path multisig, ECDSA, key recovery and ECDH were out of scope for build 97, and a backup that carries shared-account records is refused rather than restored without them.

Use Apple where it fits. Keep the library independent.

CryptoKit supplies SHA-256, which the module uses for BIP340's tagged hashes; Security supplies secure randomness. Apple's public P-256 APIs use a different curve from Bitcoin's secp256k1. They do not provide a drop-in BIP340 signer. Native Swift here means owning the Bitcoin curve implementation in Swift, while using supported platform services.

We want the package to build and test without Winnow, and to be useful beyond this app. A possible contribution to Apple's Swift Crypto project is one direction to explore. Its current contribution rules require maintainer agreement and a usable BoringSSL implementation for new APIs. A native Swift backend therefore needs an explicit upstream decision. Apple acceptance and future CryptoKit availability are open questions.

Build 97 evidence · recorded 20 October

The build 97 validation used fixtures computed in Python integer arithmetic and by a libsecp256k1 x-only oracle. The wallet's BIP32, BIP86, BIP340 and BIP341 vectors ran unchanged through the new backend. Differential tests compared every public operation with libsecp256k1, with signatures matching byte for byte under fixed auxiliary randomness; the fuzz harness fed the same input to both backends. Its recorded signet journey created a wallet, received, sent and confirmed on a real node with the native signature, and the shipped binary linked no libsecp256k1.

On 20 October an iPhone running the App Store Winnow took build 97 from TestFlight and upgraded its live wallet in place. The wallet then received and sent, and Bitcoin mainnet accepted and mined the Swift-signed transaction, a Taproot key-path spend carrying one 64-byte BIP340 signature, at height 972,342. That signature was verified against the transaction's BIP341 sighash under the module, libsecp256k1 and BIP340's reference code.

The recorded Apple silicon Mac release-build measurements were: BIP32 public child 52 µs against the C library's 19 µs; Taproot tweak 50 µs against 22 µs; generator multiplication 37 µs against 11 µs; signing 271 µs against 26 µs; and verification 207 µs against 18 µs. These are measurements of that version and environment, not benchmarks of the later branches.

Since build 97

The current single-key research branch removes the remaining package dependency, including from its tests. The earlier libsecp256k1 comparisons remain historical evidence; current tests use recorded external vectors, while fuzzing checks agreement among the module's own operations. Those internal checks do not replace an independent implementation. This does not establish constant-time execution or safe secret erasure.

PR #235, now closed, added native MuSig2 n-of-n accounts in Advanced mode. Its recorded simulator journey exchanges nonces and partial signatures with Bitcoin Core, then broadcasts and confirms the combined key-path spend. Its revision dae4b745 was uploaded to internal TestFlight as v0.8.8 by the successful release workflow. That upload does not establish a physical-device signing test, and the PR is now a parked draft. Script-path multisig and Ledger signing follow a separate line, released internally as v0.8.9, v0.8.10 and v0.8.11. Draft PR #241 proposes that whole line as one change to the wallet's main branch; internal TestFlight v0.8.11 was built from commit 7b7ff30 of that line. None of these builds includes MuSig2 accounts, and none is an App Store release.

The next experiments, as planned on 21 October

  1. Constant time and secret lifetimes. Replace the conditional subtractions, the per-bit branch in scalar multiplication and the secret-indexed table lookup with constant-time selects, clear the scalar copies made while signing and tweaking, and measure what that costs.
  2. Review the expanded signing surface. Keep the external vector provenance and test script-path and recovery-leaf signing against an independent signer, and the MuSig2 session lifecycle, cancellation and nonce consumption if PR #235 resumes. Repeat device validation for the exact candidate revision before widening distribution.
  3. Decide where it lives. A separate app identity for the single-key build, so it can be installed beside Winnow; whether the module becomes an independent package or an upstream contribution; and whether the script-path line in PR #241 should replace the App Store build, which would remove that build's MuSig2 savings and shared-account vaults. Silent Payments would add secret ECDH and still needs its own design and evidence.
03 / RECOVERYEarly development · as of 2 November

Give an old wallet
a way forward.

Winnow Rescue explores how to move funds from older Bitcoin wallet backups into an account the owner already controls.

A backup can outlive the software that created it. Recovery means understanding its format, finding the right keys and outputs, and showing the owner exactly where the money will go. That work deserves a focused tool with explicit limits for every supported format.

Winnow Rescue is being developed separately, with an embeddable Rust core, a command-line interface, and a desktop graphical interface. Its intended destination is an existing Taproot account. Keeping recovery in its own tool lets it address older wallet formats without adding those formats to the everyday phone wallet.

Current core and first-pass evidence

Since the first pass, Rescue revision 2ee03b5 has gained input parsing, derivation plans, header and coin-proof checks, and a resumable discovery engine. Its network adapter and complete import-and-sweep flow remain unfinished. These advances were source-reviewed, not exercised by a new end-to-end recovery test.

The separate recovery study ran 23 Winnow import tests, 23 historical range-scan tests, and 18 synthetic state-model tests. That establishes specific library and model behavior, not a completed Rescue flow or a live cloud restore. Read the recorded scope.

The next experiment

Start with one specified backup format and preserve its derivation and discovery information. Take it through a reproducible test-coin recovery: discover the funds, review the destination, fee and privacy disclosures, sign, and verify the payment. Test damaged backups, wrong passwords and interrupted scans. Existing range-scan code must be connected to an explicit recovery policy before it becomes a words-only restore.

04 / BITCOIN SCRIPTSProtocol research · as of 2 November

Understand a different
way to commit.

Pay-to-Merkle-Root asks what changes when an output commits directly to a tree of spending scripts.

BIP360 proposes P2MR: script-tree spending without Taproot's key-path spend. We want to understand the consequences for wallet policy, backups, interoperability, and an eventual opt-in migration.

Removing the exposed output key addresses one part of the long-term public-key exposure problem. It does not replace the signatures inside the scripts with post-quantum signatures. That distinction matters when explaining what the proposal could protect.

What the first pass established

Seven published P2MR constructions were reproduced, and 83 additional construction and partial-rule checks passed. These tests do not execute the full script rules. In the inspected draft, a depth-zero proof succeeds after matching the commitment without executing its script; a single-leaf CHECKSIG example therefore cannot demonstrate signature enforcement. Read the results and pinned proposal.

BIP360 remains a draft proposal. Winnow's tested address-based funding API rejects witness-version-2 destinations. No Bitcoin activation or shipping support is implied.

The next experiment

Restore a versioned two-leaf policy to the same address, then check successful and deliberately corrupted spends against an implementation that enforces the full pinned draft. Record those custom rules: acceptance on an ordinary regtest node does not prove P2MR enforcement. Test migration and policy backup separately.

05 / SIGNING DEVICESLedger ships

Work with the hardware
people already own.

Can Winnow coordinate payments with an independent signing device, while keeping approval and recovery understandable?

A separate signer can give a wallet a different boundary for key custody. That only helps if the phone and device agree on the account, receiving addresses, spending policy, and transaction being approved. We are researching compatibility with existing hardware wallets.

The full flow matters: what the device can display and verify, how signing messages travel, how shared-signing nonces are used once, and what happens when approval fails. Recovery must cover a lost phone, a replaced signer, and the backups needed to reconstruct the same policy.

Where it stands · 17 November

A Ledger is a signer of Winnow's Taproot k-of-n accounts over Bluetooth (Bitcoin app 2.1.2 or later; 2.2.1 for a recovery path), paired under Settings → Security → Hardware wallets and keys. Winnow registers the account on it, and the Ledger shows the address and the payment on its own screen before it signs. Since 0.9.12, with Bluetooth allowed, a Ledger in range while Winnow is open brings a card whose Set up pairs it, creates a 2-of-2 of this phone and the Ledger, registers it and has the owner compare the first address on both screens. A Ledger cannot sign for a SegWit v0 account from Winnow. On 26 October 2026 the owner's Nano X co-signed a mainnet 2-of-2 spend, mined in block 973,281, with the Swift app (0.8.14). The Lean app's CI pairs, verifies and spends with a simulated Ledger; a phone upgraded from the Swift app pairs its Ledger again.

History · recorded 21 October

The Satochip first-pass reproduction exercised four saved-account recovery variants and checked their spends with Bitcoin Core's regtest mempool acceptance. It reproduced a nonce-counter defect in the historical applet; a temporary patch passed the same checks. This was simulation, without broadcast, fresh coin discovery, a physical card, or an iPhone NFC test. The preserved PR #224 remains closed and unmerged.

The newer Ledger integration, PR #237 (since closed), built on the script-path multisig branch. It adds pairing, account registration, address confirmation and PSBT signing for a Taproot 2-of-2 account in Advanced mode. Published Ledger policy/address vectors and a local device simulator pass; no physical Ledger result has been recorded. The simulator was written from the same documentation as the client, so agreement does not establish device interoperability. Revision cbe9a976 was uploaded to internal TestFlight as v0.8.9 by the successful release workflow. Later internal builds, v0.8.10 and v0.8.11, let a Ledger be one signer of a 2-of-3 and register an account's recovery leaf with it; that leaf is miniscript, which needs Bitcoin app 2.2.0 or later, and a leaf that reuses signers on /<2;3>/* needs 2.2.1, because earlier versions return wrong leaf hashes for keys on that kind of path. These are internal test builds, not an App Store release or a demonstrated physical Ledger flow.

Why a Ledger: SeedSigner 0.8.7 refuses any input key inside a Taproot script tree, and its PSBT trim keeps only final witnesses and ECDSA partial signatures, so a script-path signature would not survive the return trip. The SeedSigner fork that signs with a Satochip card reads only non-Taproot key derivations and returns DER ECDSA signatures. Ledger's Bitcoin app signs multi_a and sortedmulti_a leaves from version 2.1.2.

The client links no Ledger code. It follows the app's command protocol: the phone sends Merkle commitments and answers the device's requests for each preimage, proof or list element. Accounts register as BIP388 wallet policies, which accept only extended keys, so the unspendable internal key is an xpub built the way Liana builds it: BIP341's NUMS point with the SHA-256 of the signers' keys as chain code. A Ledger signature is kept only after it verifies against the sighash the phone computes.

The next experiment

The Nano X step planned on 21 October is done: the mainnet 2-of-2 above. Next, record the same flow with the Lean app and a physical Nano X, naming the firmware, Bitcoin app version and app revision. Then test refusal, disconnects, retries, a lost phone and a replacement signer. The Bitcoin Core cosigner flow, retired in 0.8.13, remains separate, historical evidence.

06 / PAYMENT PRIVACYSending ships · a card for one person

Receive repeatedly.
Reveal less.

Can reusable payment information fit a wallet that discovers its own payments on a phone?

BIP352 Silent Payments lets a recipient publish reusable payment information while senders derive separate on-chain output keys. The motivation is to make repeated receiving more practical without putting the same receiving address into every payment.

The tradeoff is discovery. A recipient needs to identify payments intended for them using transaction input information and their scanning key. For Winnow, the research question includes how that work fits its direct-to-peer design, the cost of restoring a wallet, and what the phone must download and compute. Ordinary compact filters alone do not provide everything needed for discovery.

Winnow sends silent payments, since 0.8.13: Send accepts a BIP352 code (sp1…) and pays it to an address made for that transaction alone. Receiving a standard silent payment is not supported: Winnow does not scan for them. Sending needs a shared-secret calculation (ECDH) with the sender's input keys; in the Lean app it runs on Winnow's own curve code, Lean/SecpCt.

Since 0.9.14 Winnow answers the receiving question another way, for one payer at a time and without scanning: a card for one person. A silent payment's payer makes a shared secret from the recipient's scan key and the coins being spent, which is why the recipient has to scan. Here the recipient makes that shared secret beforehand, one for each person, and hands it over on a card, with a spend key made for that person (BIP352's labelled spend key). The wallet therefore knows each payment's address before it is paid and finds it through compact filters. A card holds neither of the wallet's keys, and two cards of one wallet have no byte in common. The earlier card, which carried the wallet's account key and was the same for everybody, is no longer made. On Receive, under From one person, a name gives that person an ordinary address and their card.

The costs are stated in the proposal, with what it was compared with and what is still open. A standard silent payment scan does not find these outputs. A wallet that holds only its account key cannot make a card. Anyone who has a person's address and card can see what is paid with them.

What the first pass established

The BIP352 reference runner passed 28 sending and 29 receiving cases across 28 scenarios. Sixteen added fixtures tested discovery and recovery: a missing large label hid a payment, a false helper-supplied point hid a payment, and dropping an earlier matching output hid a later one. These are reference and fixture results, not independent wallet interoperability or measured phone performance. Read the results and data requirements.

At the revision the first pass inspected, Winnow's payment API rejected Silent Payments destinations. Sending has shipped since 0.8.13. In the Lean app, silent-payment-test runs in CI, and the silentPaymentSend journey pays a code: the node's transaction pays the one output a receiver written from the BIP's receiving side finds. Scanning and restoration remain unimplemented. Its v0 rules also exclude transactions spending witness versions above 1, so P2MR inputs cannot simply be added to the same flow.

Cards · 17 November

On the 0.9.16 line, card-keys-test holds the card's derivation to vectors written without the wallet's code. card-regtest runs the wallet against a regtest Bitcoin Core as the payer: payments found through its basic filters, replaced, reorganised, spent by the issuer alone, and recovered from the phrase by a scan back. The cardForOnePerson journey makes a card for one person in the app; the node, holding only the card's text, pays its first two addresses, and Activity names both payments as that person's. This is regtest and simulator evidence.

The next experiment

Receiving a standard silent payment is still the open question. Complete an independent test-coin scan, spend and seed-plus-label restore with an explicit source of transaction input data. Preserve change label 0 and every used label or a complete generation rule. Test incomplete data, interrupted scans and chain reorganizations before measuring phone time, data and energy. Any helper must be evaluated for both privacy and its ability to hide receipts by omission.

07 / SPENDING POLICYShipped in 0.8.13

Not every key,
not right away.

Can a phone wallet support any k of n signers and delayed recovery, while making every available spending path clear?

Winnow builds k-of-n accounts with an optional delayed recovery path, under Settings → Security → Multisig accounts; they shipped in 0.8.13 and the Lean app carries them. The accounts it builds use tr(NUMS, sortedmulti_a(k, …)): the internal key is unspendable, so every spend goes through a leaf. Create an account chooses who signs (this phone, a Ledger paired under Settings → Security → Hardware wallets and keys, keys someone sent) and how many must sign; Join an account pastes one shared with you. Since 0.9.16 Join an account also takes a SegWit v0 account, wsh(sortedmulti(k, KEY, …)), for a wallet one of whose keys is a single fixed key that signs only with ECDSA: Winnow checks and signs a PSBT someone else built, and builds no payment for such an account. A Bitcoin Core wallet can hold one key of an account. MuSig2 accounts were removed in 0.8.13, so no account combines a cooperative MuSig2 key path with fallback leaves.

Each threshold signer makes an ordinary BIP340 signature over the script-path message, independently and in any order. The accounts use descriptor trees, BIP371 PSBT fields, witness assembly, account storage and backup handling. Winnow checks the leaf commitment and each signature before finalization, with the existing checks for signer independence, change ownership and the internal key.

A recovery leaf is now built for relative, block-based locks. It is and_v(v:pk(K),older(N)) or and_v(v:multi_a(m,…),older(N)), with N from 1 to 65,535 blocks, and lets a coin that has not moved for N blocks be spent either by fewer of the same signers or by a separate recovery key. Reused signers sign the recovery leaf from their own derivation branch, /<2;3>/*, so no derived key appears in both leaves, as BIP388 wallet policies require. A spend chooses its path through each input's sequence number; a recovery spend selects only coins at least N blocks deep, and review refuses a mix of paths or a coin that is too young. Absolute locks such as after(), time-based relative locks and a refresh policy are not built.

Now · 17 November

In the Lean app's CI, multisig-test and multisig-app-test run in every run, multisig-differential compares accounts with a disposable regtest Bitcoin Core, segwit-test holds SegWit v0 accounts and the ECDSA under them to published vectors and segwit-regtest holds them to a regtest Bitcoin Core, and the multisigTwoOfThreeWithRecovery journey, headless and on the simulator, builds a 2-of-3 with two Bitcoin Core wallets in the app. Its first address is Core's; the phone and both Cores sign, and Core accepts a witness with exactly two signatures. After the one-day delay the phone alone spends on the recovery path. This is simulator and regtest evidence.

History: the Swift branch · recorded 21 October

At revision a32cc92, the passing CI journey exercises a 2-of-2 script-path account in the simulator with Bitcoin Core as the second signer. Addresses agree, the phone cannot broadcast with one signature, Core cosigns, and the spend is accepted and mined on the test signet. The account API supports k-of-n; this journey demonstrates the particular 2-of-2 flow.

At revision 5074341, tests compare four timelocked descriptors with the checksums and addresses Bitcoin Core 31.1 produced for them. The signet journey in the successful release workflow gives its 2-of-2 account a three-block recovery leaf that either signer can use alone; after the delay the phone spends by itself, and Core accepts and mines the CSV-locked witness. That revision is internal TestFlight v0.8.10. v0.8.11, from a later release workflow, adds four account-sync fixes: a zero-value output no longer stalls sync, a spend that loses to a confirmed conflict is undone, accounts watch a full gap limit ahead, and a reorg keeps a fallen spend's inputs reserved. All of this is simulator and signet evidence; no physical device has signed a recovery spend.

The script-path line needed no curve code: between 3794057 and 7b7ff30 the NativeSecp256k1 Swift files are unchanged, while non-blank production Swift grows from 24,476 to 28,788 lines (WalletCore 15,901 to 18,176, the app 7,794 to 9,831). The MuSig2 branch grew the module from 781 to 843 lines. Testing against Bitcoin Core found one disagreement: Core writes a two-leaf tree into a PSBT output in reverse leaf order. Both orders are valid, but Winnow's combiner refused a field with two values, so Winnow now writes Core's order and the combiner stays strict.

The next experiments

  1. Recovery that stays usable. A relative lock counts from each coin's own confirmation, so keeping the main path primary means moving coins before their locks mature. Decide when the phone should prompt that refresh, then spend a matured recovery leaf with a physical Ledger.
  2. A policy people can read. Show who can spend, and when, before anyone funds the account. Extend the ported policy checks to every combined path and its regression cases. The display question is shared with hardware wallets.
  3. FROST, watched. Threshold Schnorr signatures would keep k-of-n on the key path. Follow its Bitcoin standardization rather than adopt it early.

A question shared by every project

What must survive
the lost device?

A recovery strategy must account for signing authority, coin discovery, spending policy, and any state required to sign safely. Winnow's emphasis on local discovery and Rescue's broader recovery task require separate privacy evaluations: asking a server about wallet-specific scripts or combining coins in a sweep can disclose relationships.

Hash-based signatures make this distinction especially important. SPHINCS+-based SLH-DSA is stateless, but a wallet still needs recoverable keys and account information. Stateful schemes such as XMSS and LMS also require a reliable record of used one-time signing keys. Restoring an old backup can roll that record backward; a chain rescan cannot reveal every signature exported before the device was lost.

The 18-test synthetic model now reproduces this failure: both a stale restore and an independent clone reuse a signing slot even while the chain shows no signature. Its coordinated case assumes atomic reservations and a shared authority that cannot roll back; it does not implement that storage guarantee. These remain research questions, not supported post-quantum recovery flows in Winnow or Rescue.
